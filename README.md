# 招标参数自动偏离表生成器

把招标文件里的技术要求逐条抽出来，与自家产品参数比对，自动判定「响应 / 正偏离 / 负偏离」，  
输出可直接编辑的偏离表。

**动机**：一份 30-80 项参数的偏离表，人工做要 4 小时，且容易漏项、判错方向。  
这个工具把它压到分钟级，并且把不确定的条目单独列出来给人复核。

## 步骤 5.6：单项目定稿（工具给初稿，人定口径）

`scripts/09_make_sishi_report.py` 演示了「正式投标」该怎么用这套工具：

1. 08 切出招标条款原文（`data/params_tender.json`）
2. 06 自动判定出第一稿（哪几条要人看，一目了然）
3. 人拿着白皮书/检验报告/说明书/配置清单**逐条核定**，写进
   `data/sishi_decisions.json`：判定 + 响应文案 + 页码级出处 + 存疑原因与建议
4. 09 合并两份数据，调用 07 的同一套排版生成最终表

分工很清楚：**工具负责不遗漏、不抄错数字、出处可查；人负责口径判断**
（比如「标称 500mJ vs 实测 490mJ 该怎么报」「安卓屏还是 Linux 屏」这类
涉及废标风险的判断，永远不能交给模型）。

第四师医院项目实测：18 条 → 响应 9 / 正偏离 2 / 负偏离 1 / 存疑 6，
每条响应都带页码级索引，存疑 6 条各写了具体处理办法。

## 步骤 5.5：招标文件 Word 直读

真实需求是「把招标文件 Word 丢进来，直接出偏离表」，不是先手工做参数表 Excel。  
新增 `scripts/08_parse_tender_docx.py`，思路仍是「代码找结构，LLM 理解语义」：

1. 找设备小节标题：「（三）皮秒激光治疗仪」这种格式（一份标书里往往混着  
   无影灯、取皮植皮、CO2 等多台设备，按关键词定位目标小节）
2. 小节内按条款编号切分，多行条款合并（控制系统一条占 4 段），  
   ▲/★ 从编号前后两个位置都能认
3. 切出的条款走 03→06→07 原流水线，后面零改动

实测（第四师医院招标文件，1362 段，皮秒 18 条，33 秒出表）。  
这次真实数据逼出了三个引擎修复（都有单测）：

- **波长允差误判负偏离**：「1064nm±5nm」里的允差 ±5 被当成要求波长 5nm。  
  修复：波长分支只认 ≥100 的数字。这类 bug 又一次验证了那句话——  
  在单一数据源上永远不出现，一换输入就暴露。
- **上限承诺 vs 区间要求**：产品「脉宽≤248ps」vs 要求「350-500ps」，  
  旧的区间逻辑会判负偏离，实际是优于要求。修复：产品侧是单点上限/下限承诺  
  且优于要求区间端点时判正偏离，理由里写明「上限承诺」。
- **产品描述里抠数值**：要求「≥7关节」vs 产品「七关节平衡式导光臂」——  
  产品侧是文字描述带中文数字，新增 feature→数值的降级解析。

其余差异（治疗手具、能量调节方式、配置清单等）如实落在存疑清单，  
那本来就是给人复核的。

## 步骤 5：Web 服务（上传 Excel → 网页看结果 → 下载 Word）

跑批要 1~2 分钟，HTTP 不能同步等，用的是「提交任务 + 轮询进度」模式：

```
POST /api/jobs          上传 Excel，立刻返回任务号
GET  /api/jobs/{id}     轮询进度（日志实时可见）与判定结果
GET  /api/jobs/{id}/docx     下载生成的 Word
POST /api/extract       单条要求快速抽取（调试用）
GET  /api/health        健康检查
```

启动（浏览器打开 <http://127.0.0.1:8000> ）：

```bash
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

端到端实测：真实皮秒参数表 31 条，54 秒跑完，31/31 抽取成功，Word 下载正常。  
注意每次跑批 LLM 输出有随机性，个别功能类条目可能在「响应/存疑」间波动——  
这正说明存疑清单要人工过一遍，工具的边界是设计出来的。

**Docker 的决定**：本机 Win10 1909 / 8G 内存跑不动 Docker Desktop（无 WSL），  
所以服务本机用 uvicorn 跑；`Dockerfile` 已写好并经过 .dockerignore 安全审查  
（.env、真实标书一律不进镜像），日后部署到公司服务器 `docker build` 即用。

架构上这次重构的意义：`06_compare.run_compare()` 和 `07_make_docx.build_document()`  
成为命令行和 API 共用的唯一实现——判定与排版逻辑只写一份，不会再出现  
「脚本里改了、接口里漏了」的两份拷贝 bug（步骤 4 里刚吃过这种亏）。

## 步骤 4：证明材料索引（精确到页与条）

偏离表的「证明资料及索引」列不是写文件名就完事——招标文件要求指到「第X页第X条」，  
指不到条，评委翻不到，等于没提供证明。

`data/evidence_map.json` 是索引的唯一数据源，按参数名登记每条要求的权威出处：

```json
"峰值功率": [
  {"doc": "检验报告", "loc": "第4页 序号7（条款2.7）", "detail": "1064nm 2.00GW、532nm 1.01GW，允差±20%"},
  {"doc": "使用说明书", "loc": "第14页 3.2.5", "detail": "1064nm 2.00GW"}
]
```

出处分级（可信度从高到低）：**检验报告 > 说明书/注册证 > 配置清单 > 技术白皮书**。  
性能指标只认检验报告；白皮书只能证明「有这功能」，不能证明「达到这个数」。

生成物里对应三张表：

1. 偏离表正文 —— 索引列精简到 1~2 条主出处
2. **附二 证明材料索引明细** —— 每条出处的页码、序号/条款、该处载明的具体数值（评委核查用）
3. 存疑清单 —— 出处覆盖不全或无出处的条目，写明缺什么、去哪补

`unavailable: true` 的条目（当前是「设备重量」「防护镜光密度」）会显式标注  
**【待补件】**，因为现有资料确实无法支撑——这种情况下编一个出处，比留空危险得多。

## 评测结果

| 样本集      | 条数 | operator 准确率      | is_measurable 准确率 | 错例 |
| -------- | -- | ----------------- | ----------------- | -- |
| 皮秒（同源样本） | 31 | 100% (29/29)      | 100% (31/31)      | 0  |
| 光子（困难样本） | 18 | **94.4% (17/18)** | 100% (18/18)      | 1  |

**唯一错例（光子行 17）**：「最大支持10个子脉冲」——模型输出 `>=`，正确为 `<=`，  
比较方向完全反转。困难样本（表达方式不同的另一份招标文件）成功暴露了同源样本上  
发现不了的问题。

**评测方法**：只评 operator 和 is_measurable 两个决策关键字段（param_name 写法不影响  
投标判定）；人工盲标与模型推理隔离；5 处人工-模型分歧逐条仲裁，仲裁原则为「以招标  
真实意图为准，不以文字表面为准」；标注内部矛盾（如可量化=是但 operator=none）按标注  
错误修正。评测对齐业务目标，不对齐模型输出格式。

## 两个真实 bug（都是被真实数据逼出来的）

**1. 别名映射写了两份** —— 「脉冲脉宽 → 最小脉冲宽度」的映射在判定脚本和文档生成脚本里各写  
一份，改一处漏一处，导致正偏离条目的响应内容为空。修复：抽成 `param_alias.py` 单一数据源。

**2. 单位没归一化，判定方向反转** —— 招标写「发散角 < 0.3 弧度」，产品库写「≤150mrad」，  
两个数直接比大小，150 > 0.3，把正偏离判成了**负偏离**。修复：`06_compare.py` 增加 `UNITS`  
换算表，统一换算到招标文件的单位再比较（结论里显示「0.15弧度 < 0.3弧度」，评委看得懂）。  
量表之外的量纲组合一律判存疑，绝不猜。

这两个 bug 的共同点：**在单一数据源上永远不会出现，一换输入就暴露**。这也是为什么  
工具类项目必须拿真实标书跑，不能只跑自己造的例子。
